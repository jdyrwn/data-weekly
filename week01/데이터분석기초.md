## Q1. 데이터 분석가에게 가장 중요한 역량
 
> 기술적 역량과 비기술적 역량 중 하나를 선택하고, 그 이유를 본인의 언어로 설명해 보세요.
 
### 💡 내 선택: 비기술적 역량
- 문제를 정의하는 **기획력**, 그리고 데이터 안팎의 인과관계를 **다각도로 바라보는 시야**
### 이유
1. 데이터를 추출하고 가공하는 작업은 AI의 도움으로 점점 빠르고 쉬워지고 있다.
2. 그렇다고 기술이 필요 없다는 뜻은 아니다. 기술을 충분히 이해하고 있어야 AI를 효율적으로 활용할 수 있고, AI가 낸 결과의 오류도 검증할 수 있다. 기술은 갖춰야 할 **기본기**다.
3. 하지만 같은 데이터를 보고도 유의미한 인사이트를 뽑아내는 힘은 결국 **무엇을 물어볼지 정하는 능력**에서 나온다. 도메인을 이해하고 목표와 우선순위를 정하는 기획력이 분석의 방향을 결정한다.
4. 또 숫자로 드러난 데이터만 보면 진짜 원인을 놓칠 수 있다. 데이터 밖에 다른 원인은 없는지 폭넓게 해석하는 시야가 필요하다.
### 예시
- 이륜 모빌리티 서비스에서 특정 날 이용량이 갑자기 줄었다고 하자. 서비스 내부 데이터만 보면 앱 오류나 가격 정책 같은 원인을 먼저 의심하게 된다.
- 하지만 그날 갑작스러운 소나기가 내렸다면, 이용량 감소는 서비스 문제가 아니라 **날씨의 영향**일 수 있다.
- 이처럼 데이터 바깥의 맥락까지 함께 살펴야 잘못된 결론을 내리거나 불필요한 대응을 하는 일을 피할 수 있다.

## Q2. 피벗 테이블 vs SUMIF·COUNTIF
 
> 어느 쪽이 더 좋다고 생각하나요? 선택한 이유와 함께 설명해 보세요.
 
### 💡 내 생각: 목적과 데이터 구조에 따라 다르다
- **데이터를 탐색하며 한눈에 훑어볼 때는 피벗 테이블**, **원하는 형태로 고정된 표를 만들거나 특정 조건만 정확히 뽑을 때는 수식**이 더 편하다.
- 실무에서도 둘 중 하나만 쓰기보다, 피벗으로 탐색하고 수식으로 보고서를 만드는 식으로 함께 쓰는 경우가 많다.
### 두 방식 비교
| | 피벗 테이블 | SUMIF·COUNTIF (SUMIFS·COUNTIFS) |
|---|---|---|
| 장점 | 데이터 범위만 선택하면 수식 없이 빠르게 표를 만들 수 있다<br>카테고리별 자동 그룹화가 쉽다<br>필터로 기준을 바꿔가며 여러 관점으로 볼 수 있다 | 표의 형태(레이아웃)를 내가 직접 설계할 수 있다<br>원본이 바뀌면 결과도 바로 다시 계산된다<br>계산 결과를 다른 수식에 넘겨 이어서 쓰기 좋다 |
| 단점 | 원본 데이터를 고쳐도 자동으로 다시 계산되지 않아 '새로 고침'이 필요하다<br>표의 모양을 원하는 대로 바꾸기 어렵다 | 칸마다 수식을 써야 해서 손이 많이 간다<br>조건이 많아지면 수식이 길어지고 실수하기 쉽다<br>행·열 기준값(카테고리 목록)을 직접 만들어야 한다 |
| 어울리는 상황 | 처음 받은 데이터를 이리저리 쪼개 보는 **탐색 단계**, 질문에 한 번 답하는 분석 | 매주·매달 같은 양식으로 나가는 **정기 보고서**, 여러 조건을 조합한 특정 수치 |
 
### 이유
1. **피벗 테이블은 탐색에 강하다.** 호텔 예약 데이터를 분석할 때 정제 시트의 데이터를 카테고리별로 분류해 한 번에 뽑을 때는 피벗 테이블이 편했다. 칸마다 수식을 쓰지 않아도 되고, 호텔 타입처럼 기준을 필터로 걸었다 뺐다 하며 빠르게 한눈에 볼 수 있었다.
2. **수식은 정밀함과 고정된 양식에 강하다.** 특정 내용만 보고 싶거나 여러 조건을 동시에 걸고 싶을 때는 수식으로 만든 표가 더 편했다. 내가 원하는 칸에 원하는 조건의 값을 정확히 넣을 수 있기 때문이다.
3. **둘은 서로 검증하는 데에도 쓸 수 있다.** 피벗 테이블의 숫자가 맞는지 확인하고 싶을 때, 셀 하나를 SUMIFS로 다시 계산해 비교해 볼 수 있다.
### 참고: SUMIF vs SUMIFS
- `SUMIF`는 조건을 하나만, `SUMIFS`는 여러 개 쓸 수 있다. `SUMIFS`는 조건이 하나여도 똑같이 동작한다.
- 인수 순서가 다르니 주의한다. `SUMIF`는 더할 범위가 **마지막**, `SUMIFS`는 더할 범위가 **처음**에 온다.
```
=SUMIF(조건범위, 조건, 합계범위)
=SUMIFS(합계범위, 조건범위1, 조건1, 조건범위2, 조건2, ...)
 
예) 호텔 타입이 "City Hotel"이고 취소되지 않은 예약의 숙박일수 합계
=SUMIFS(숙박일수, 호텔타입, "City Hotel", 취소여부, 0)
```
 
> 💡 원본 범위를 `Cmnd + T`로 '표'로 만들어 두면, 데이터가 추가되어도 피벗 테이블과 수식의 범위가 자동으로 늘어난다.

## Q3. 리스트와 딕셔너리
 
> 어떤 상황에서 각각 사용하나요? 데이터 분석 업무를 예시로 들어 설명해 보세요.
 
### 💡 한 줄 정리
- 둘 다 여러 데이터를 묶어서 관리할 때 쓴다.
- **"몇 번째인가"가 중요하면 리스트**, **"무엇(이름표)인가"가 중요하면 딕셔너리**를 쓴다.
### 개념 비교
| | 리스트 `[ ]` | 딕셔너리 `{ }` |
|---|---|---|
| 구조 | 0번부터 시작하는 순서가 있는 목록 | **키(Key)** 와 **값(Value)** 의 쌍 |
| 값을 찾는 방법 | 인덱스(번호)로 꺼낸다 `a[0]`<br>특정 값이 있는지 찾으려면 처음부터 하나씩 확인해야 한다 | 키로 바로 꺼낸다 `d["key"]`<br>처음부터 훑지 않고 키로 바로 찾기 때문에, 데이터가 많아도 빠르다 |
| 중복 | 같은 값을 여러 번 넣을 수 있다 | 키는 중복될 수 없다 (같은 키로 넣으면 값이 덮어써진다), 값은 중복 가능 |
| 순서 | 넣은 순서가 유지된다 | 파이썬 3.7부터 넣은 순서가 유지된다 |
 
### 데이터 분석 업무 예시 (호텔 예약 데이터)
- **리스트를 쓰는 경우:** 순서가 있거나, 같은 종류의 값을 나열할 때
  - 분석에 사용할 컬럼 목록만 골라내기
  - 월(月)처럼 순서가 중요한 값 정렬하기
  - 여러 파일을 반복문으로 하나씩 불러오기
- **딕셔너리를 쓰는 경우:** 이름표(키)로 값을 찾거나 바꿀 때
  - 코드값을 사람이 읽을 수 있는 이름으로 바꾸기 (매핑)
  - 컬럼 이름을 한글로 바꾸기
  - 컬럼마다 다른 값으로 결측값 채우기
  - 호텔 타입별 집계 결과처럼 "기준: 값" 형태로 정리하기

## Q4. 결측값 처리
 
> 결측값을 무조건 제거하는 것이 왜 위험할 수 있는지, 본인이라면 어떤 기준으로 처리 방법을 결정하겠는지 설명해 보세요.
 
### 💡 한 줄 결론
- 결측값은 지우기 전에 **"왜 비어 있는지"** 를 먼저 확인해야 한다. 빈칸이 누락인지, 오류인지, 아니면 원래 없어야 하는 값인지에 따라 처리 방법이 달라진다.
### 무조건 제거하면 위험한 이유
1. **다른 중요한 데이터까지 함께 사라진다.** 한 칸만 비어 있어도 그 행 전체를 지우면, 나머지 컬럼에 있던 멀쩡한 정보까지 잃게 된다.
2. **결과가 한쪽으로 치우칠 수 있다(편향).** 결측이 무작위로 생기는 경우는 드물다. 특정 집단에만 결측이 몰려 있다면, 지우는 순간 그 집단이 통째로 빠져 남은 데이터가 전체를 대표하지 못한다.
3. **빈칸 자체가 정보일 수 있다.** 예를 들어 '쿠폰 사용일'이 비어 있다면 대개 쿠폰을 쓰지 않았다는 뜻이다.
### 예시: 본인인증 정보가 없는 과거 가입자
- 예전에 일했던 서비스에서는 가입(로그인) 시 받는 정보가 중간에 바뀌어서, 과거에 가입한 유저들에게는 **본인인증 정보가 없었다.**
- 이 빈칸은 입력 실수나 시스템 오류가 아니라, **그 당시에는 수집하지 않았던 값**이다. 결측은 맞지만, 원인이 '가입 시기'로 분명하게 설명된다.
- 이것을 결측값이라고 무조건 삭제하면 **과거 가입자 전체가 분석에서 빠진다.** 그러면 이 유저들의 이용 기록이나 다른 데이터를 추적할 때 오류가 생기고, 최근 가입자 위주로 치우친 결론을 내리게 된다.
- 이런 경우에는 삭제하기보다 `본인인증_수집이전` 같은 별도 값이나 플래그를 두고, 분석 목적에 따라 따로 구분해서 보는 것이 맞다.
### 나의 처리 기준
1. **어떤 데이터가, 왜 비었는지 확인한다.** 단순 누락인지, 진짜 오류인지, 원래 없어야 하는 값(수집 이전, 해당 없음)인지 구분한다.
2. **결측 패턴을 확인한다.** 결측이 무작위인지, 특정 집단(가입 시기, 기기, 지역 등)에 몰려 있는지 살펴본다.
3. **도메인 지식을 활용한다.** 서비스 정책 변경 이력처럼 데이터 밖의 맥락으로 결측의 이유를 설명할 수 있는지 확인한다.
4. **데이터 손실을 최소화한다.** 가능한 한 많은 정보를 보존하는 방향으로 처리하고, 중요한 분석이라면 여러 처리 방법을 시도해 결과를 비교한다.
| 상황 | 처리 방법 |
|---|---|
| 결측이 아주 적고 무작위로 보일 때 | 해당 행 삭제 |
| 숫자 컬럼, 이상치가 있을 때 | 중앙값으로 대체 (가능하면 그룹별로) |
| 범주형 컬럼 | 최빈값으로 대체하거나 `미응답` 같은 새 범주 만들기 |
| 시간 순서가 있는 데이터 | 앞뒤 값으로 채우기 (`ffill`, `bfill`) |
| 빈칸 자체에 의미가 있을 때 (수집 이전, 해당 없음) | 삭제하지 않고 `결측여부` 플래그 컬럼 추가 |
